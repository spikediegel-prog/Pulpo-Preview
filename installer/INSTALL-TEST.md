# Pulpo Preview disk installer — install test

How the installer was proven to install, and what the test does
*not* prove. The boot test (`BOOT-TEST.md`) proves the ISO boots;
this file proves it installs.

## Method

`installer/install-test.sh` runs two phases under QEMU + OVMF
(UEFI firmware), with no KVM — neither VM has `/dev/kvm`, so
QEMU runs in TCG and everything is slow. Guest: 2048 MB RAM,
2 vCPUs, q35, `-cpu qemu64`, a 25 GB qcow2 virtual disk, and a
user-mode NIC (`-netdev user` — NAT only, no inbound
connections). The NIC is deliberate: the pulpo-config import
derives the interface from the live session's default route, and
without a NIC there is no interface for the network part of the
config. The boot test's `-net none` does not apply here.

The installer is driven by hand through the QEMU monitor
(`--shot` / `--key` / `--type` / `--mouse` subcommands). A GUI
installer under TCG is not scriptable reliably — timing varies
by minutes — so the script holds the VM up and the operator
drives it, taking a screenshot at each step. The evidence is
the screenshots + the logs, not a script verdict.

The QEMU command attaches a USB tablet (`-device usb-tablet`)
so monitor mouse coordinates are absolute. With only the
default PS/2 mouse they are relative to the guest pointer's
last known position and clicks land in the wrong place.
A `qemu-xhci` USB controller is also attached: `-machine q35`
creates no USB bus by default, so a bare `-device usb-tablet`
makes QEMU exit immediately with "No 'usb-bus' bus found".
Keyboard is the reliable path through the wizard regardless:
`Alt+N` advances (Next), `Alt+I` starts the install from the
summary, `Enter` confirms the install dialog, `Tab` moves
between fields, and `--type` fills them. Note: `--type` does
not send `~` (tilde) — it arrives as `/` — so use full paths
(`/home/ubuntu/...`) when typing in the live session, never `~`.

### Phase install

1. Boot the ISO with the blank disk attached. Wait for the live
   desktop (gdm in `boot.log` + desktop screenshots).
2. In the live session, create the customer config first:
   open the Control Center (autostarted), Guided Setup on the
   System page, and fill in the 6 steps. For the test the
   example config is used (DHCP, America/Phoenix,
   ntp.ubuntu.com + pool.ntp.org, local evidence store
   `/var/lib/pulpo/evidence`, retention 24h / 10%,
   acknowledged). Save it. (Equivalently: copy
   `installer/pulpo-preview-config.example.json` to
   `~/.config/PulpoPreview/control-center-customer-config.json`
   in the live session — the same document the wizard writes.)
3. Open a terminal (Ctrl+Alt+T) and run `sudo -E calamares`
   (the same command the "Install Pulpo Preview" desktop icon
   runs). Confirm the desktop icon exists first
   (`ls ~/Desktop/` shows `install-pulpo.desktop`).
4. Work through Calamares: welcome (requirements pass) →
   keyboard (us) → partition (erase-disk, the default) →
   users (create the admin user; note the name + password —
   the verify phase logs in as this user) → summary → Install.
   Screenshot each step.
5. Wait for the install to finish (unpackfs copies ~11 GB
   under TCG — expect a long time; the progress bar is the
   evidence it is working). The finished page offers a restart.
6. Shut the VM down (do NOT let it reboot into the live ISO
   again — the ISO is still attached and boots first). Create
   `INSTALL_DONE` in the work dir (or `--stop` the VM).

### Phase verify

1. Boot from the virtual disk only (no ISO). The installed
   GRUB (shim + grub, EFI entry "pulpo") is what boots — this
   phase is itself the bootloader proof.
2. At gdm, log in as the user created in the install.
3. Check, in a terminal, and screenshot each result:
   - Desktop reached, Control Center opens (Qt) — the app
     autostarts on login.
   - `/etc/pulpo/customer-config.json` exists and matches the
     config from phase install (same schema, same values).
   - The user profile
     `~/.config/PulpoPreview/control-center-customer-config.json`
     exists.
   - `/etc/systemd/timesyncd.conf` carries the two NTP servers
     (`ntp.ubuntu.com`, `pool.ntp.org`).
   - `/etc/netplan/60-pulpo.yaml` exists and configures DHCP on
     the interface (`dhcp4: true`).
   - The storage record: the Control Center shows the local
     store, retention 24h / 10%, acknowledged.
   - `/var/log/pulpo-installer/` holds the install log and the
     Calamares session log.
   - `efibootmgr -v` shows the "pulpo" boot entry (and the
     ESP at `/boot/efi/EFI/pulpo/` holds `shimx64.efi`).
4. Record the results in the table below.

**What blocked it — gnome-initial-setup (GIS).** The live session autostarts `/usr/libexec/gnome-initial-setup --existing-user` (`/etc/xdg/autostart/gnome-initial-setup-first-login.desktop`, `AutostartCondition=unless-exists gnome-initial-setup-done`). Its Welcome page (orange Ubuntu logo, "Welcome!", language search) covers the desktop; the language list never loads (spinner for 40+ minutes). GIS is a modal that swallows the shell: Super, Ctrl+Alt+T, Alt+F2, Alt+Tab, Escape and Alt+F4 all have no visible effect, and the Control Center (autostarted) is never seen. Keyboard input DOES reach the guest (typing works; `--key` combos work — Ctrl+Alt+F3/F1 switch VTs), and GIS is keyboard-drivable: Welcome → Typing (English (US)) → Time Zone (Phoenix, Arizona — MST UTC-07, 16:05) → About You (Full Name "Ubuntu", Username "ubuntu", Computer "ubuntu"). From About You the "Enterprise Login" button was hit by mistake; GIS then remembers that branch — every forward navigation from Time Zone returns to Enterprise Login (three times), while Previous returns to Time Zone. There is no visible way back to the About You form from the Enterprise Login view, and Next there is disabled (no domain). The session is stuck in that loop.

**Why GIS runs at all (not fully determined).** Stock casper ships `52gnome_initial_setup` (in the squashfs `casper-bottom/` scripts, and the stock initrd is reused by this build), which is supposed to `touch /root/home/$USERNAME/.config/gnome-initial-setup-done` at boot so GIS does not autostart. GIS autostarted anyway, so either that script did not run / did not create the marker, or the marker was not visible to the session. Which of those it is was NOT determined — it needs a shell inside the guest to check whether the marker file exists. The robust build fix (not yet implemented — needs a rebuild, build #11, plus a re-test) is to bake the marker into the live image: create `/etc/skel/.config/gnome-initial-setup-done` so the live user's home has it regardless of casper-bottom, and/or disable the GIS autostart entry for the live session.

**Two harness findings from this run (both need fixing before the next run).**
- **TTY login is closed.** The live `ubuntu` user rejects an empty password AND the password `ubuntu` at the tty3/tty2 login prompt (`Login incorrect`), so there is no shell to kill GIS or inspect the guest. This is surprising: casper's `25adduser` runs `passwd -d ubuntu` (password deleted) and PAM `common-auth` carries `pam_unix.so nullok`, so an empty password should work — yet it does not. The shadow entry was not inspected (no shell). Do not guess the password; find the real state from a guest shell or the boot log before the next run.
- **The mouse is not a reliable clicker.** The pointer is invisible in QEMU screendumps (hardware cursor plane — pixel-diffs before/after `mouse_move` are 0), so its position cannot be verified from a shot. `--mouse X Y` (raw pixel coords, as written) does not land on the intended control: `--mouse 965 55` did not click Next, and a scaled `mouse_move 24700 2253` (0–32767 for (965,55)) did not either. What DID work, reproducibly (twice): home-then-move (`mouse_move -30000 -30000`, then `mouse_move 965 55`, then button 1/0) toggles the Quick Settings menu — i.e. the click lands in the top-right system area, not on Next. So clicks register, but the coordinate mapping is neither pixel-1:1 nor the assumed 0–32767 absolute. `--mouse` as written must not be trusted to click a control; settle the mapping (relative vs absolute, and any scale) and add a test before the next run. Keyboard (`--type` / `--key`) is reliable and is how GIS was driven.

**The mechanism (Calamares source, `calamares/calamares` branch `calamares`).**
- `ShellProcessJob::setConfigurationMap` warns `No script given` when the configuration map has no `script` key
  (`src/modules/shellprocess/ShellProcessJob.cpp`).
- The map comes from `Module::loadConfigurationFile(configFileName)`, which searches
  `/etc/calamares/modules/<config>` then the app-data dir's `modules/<config>` and warns
  `No config file for "<module>" found anywhere` when nothing matches
  (`src/libcalamares/modulesystem/Module.cpp`).
- The debug log shows the load for this instance searched for the BASE name only:
  `No config file for "shellprocess" found anywhere at "/home/ubuntu/src/modules/shellprocess/shellprocess.conf"`,
  `"/etc/calamares/modules/shellprocess.conf"`, `"/usr/share/calamares/modules/shellprocess.conf"` (line 122).
  The string `shellprocess_` appears NOWHERE in the 778-line debug log — Calamares never looked for
  `shellprocess_install-cc-deb.conf`.
- Why: the instance config filename is NOT derived from the instance name. `InstanceDescription` defaults to
  `key.module() + ".conf"` (`shellprocess.conf`); the instance-specific name comes only from an explicit
  `instances:` entry in `settings.conf` with a `config:` key
  (`src/libcalamares/Settings.cpp`, `InstanceDescription::fromSettings`;
  `Settings::reconcileInstancesAndSequence()` appends a default `<module>.conf` description for a custom instance
  in `sequence:` that is not listed in `instances:`).
  The repo's own `settings.conf` documents it: "`config` is optional, if none is given, `<module>.conf` is used".

**The defect in our tree (worktree main `d88ab9b`, confirmed).**
`installer/calamares/settings.conf` `instances:` (line 29) declares pulpo-config, remove-live, verify-initramfs and
grub-prefix-stub, each with `config: shellprocess_<id>.conf` — e.g.
`- id: pulpo-config / module: shellprocess / config: shellprocess_pulpo-config.conf`.
`install-cc-deb` appears ONLY in the exec sequence (line 61); it has NO `instances:` entry.
So Calamares used the default `shellprocess.conf`, found nothing, and ran the step as a silent no-op
(a shellprocess job with no script returns OK, which is why the install still said "All done.").

**Fix.** Add to `installer/calamares/settings.conf` `instances:`:
```yaml
  - id: install-cc-deb
    module: shellprocess
    config: shellprocess_install-cc-deb.conf
```
**Test gap (why PR #130 shipped this).** PR #130's tests checked the exec sequence contains
`shellprocess@install-cc-deb` and that the conf/script/bundle files exist, but nothing asserted that
`settings.conf` declares the instance → config mapping. A test that parses `settings.conf` `instances:` and
requires an entry for every custom `shellprocess@<id>` in the exec sequence, with a `config:` naming an existing
`modules/shellprocess_<id>.conf`, would have caught this. The same gap applies to any future shellprocess instance.
